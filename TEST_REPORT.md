# Проверка GPT BLE Manager

Проверки: 30 сентября — 1 октября 2026 года. Платформы библиотеки: Android и Windows JVM x64.

## 1 октября 2026: рефакторинг нативного Windows-модуля

`BleNative.cpp` разделён на 16 файлов реализации и 15 внутренних заголовков в
`ble-manager/src/windowsMain/cpp/src`. Модули: `jni`, `runtime`, `state`, `adapter`,
`bluetooth`, `scan`, `pairing`, `gatt`. Добавлены комментарии к контрактам и механике
работы, ссылки на документацию, `.clang-format` и
[описание архитектуры](ble-manager/src/windowsMain/cpp/README.md).
CMake перечисляет исходники явно; Gradle отслеживает вложенные `.cpp` и `.hpp`.
Публичный Kotlin API и версия `0.2.3-local` сохранены.

Проверки после переноса:

- `:ble-manager:allTests :ble-manager:assemble` — успешно. Windows DLL/JAR пересобраны;
  55 Windows-тестов выполнены, 45 Android host-тестов имеют успешный результат
  `UP-TO-DATE`, поскольку их исходники и зависимости не изменялись.
- CMake/CTest: один executable, шесть проверок MAC, IBuffer, UUID16/32/128,
  коротких AD-секций, порядка/повторов UUID и числового GATT-статуса — успешно.
- Сопоставление с копией исходного монолита: 70 структурных проверок пройдены.
  Сверены последовательности токенов перенесённых операций и вспомогательных функций,
  JNI-сигнатуры, fallback и все 17 имён экспортов собранной DLL.
  Проверка учитывает извлечение парсера UUID/генератора handles и добавление фигурных
  скобок форматтером; она дополняет тесты, но не доказывает отсутствие любых гонок.
- `clang-format 19 --dry-run --Werror` — успешно. MSVC `/W4` не выдал предупреждений.
  Существующее предупреждение Gradle о deprecated features остаётся.

в Maven Local в этом изменении нет.

## Версия 0.2.3-local: исправление Windows pair Failed (19)

Ошибка воспроизведена в отдельной C++/WinRT-программе на `A0:6C:65:41:61:F6`:
`Kind=AssociationEndpoint`, `IsPaired=false`, `CanPair=true`; обычный `PairAsync()`
вернул `Failed (19)`. Сохранение BluetoothLEDevice живым до конца вызова не устранило отказ.

В том же окружении `Custom.PairAsync(ConfirmOnly, Default)` вызвал `PairingRequested`
с `ConfirmOnly`. После `Accept()` вернулся `Paired (0)`, свежий запрос — `IsPaired=true`.
Этот путь перенесён в JNI. Принимается только ConfirmOnly; сравнение PIN и ввод PIN
не подтверждаются автоматически. Обработчик хранит слабую ссылку на менеджер,
проверяет закрытие и снимается через RAII при успехе, исключении или таймауте.

Сборка и все Maven Local публикации `0.2.3-local` успешны.
**55 Windows-тестов + 45 Android host-тестов = 100**, ошибок нет.

Отдельное KMP-приложение с опубликованной зависимостью скомпилировано для Android
и Windows. Реальный вызов `manager.pair(device)` вернул `Paired`; запрос после него —
`Paired`. Последующая отдельная JVM-проверка получила `Paired` до GATT-подключения,
три раза во время подключения и после его закрытия. `readDeviceName()` до и после
этих запросов возвращал `MentarisBLE`, соединение оставалось `Connected`.

Это проверка реального сопряжения Windows через библиотеку. Unpair, аппаратный
Android и PIN/passkey-сценарии в этом исправлении не проверялись. Для Windows
PIN/passkey-сопряжения используйте системные настройки.

## Версия 0.2.2-local: pair / unpair и состояние сопряжения

Добавлены `BleManager.getPairingState`, `pair`, `unpair`, типы `PairingState`,
`PairResult` и `UnpairResult`. Windows использует `DeviceInformation.Pairing`
и результаты WinRT, Android — `bondState`, `createBond` и ожидание конечного состояния.
Android unpair использует публичный `CompanionDeviceManager.removeBond` на API 36+
при существующей ассоциации текущего приложения; без поддержки возвращает
`BleError.Unsupported`. Скрытые Android API и reflection не используются.

Проверки сборки и публикация Windows/Android/KMP в Maven Local успешны.
**54 Windows-теста + 45 Android host-тестов = 99**, ошибок нет. Новые тесты покрывают
ожидание реального окончания операции, идемпотентность, синхронные события, отказ,
таймаут, отмену, закрытие менеджера, освобождение слушателя и классификацию кодов ОС.

Аппаратная проверка из отдельного потребителя опубликованной версии:

| Проверка | Результат |
| --- | --- |
| Компиляция общего API для Android и Windows | Успешно |
| `getPairingState(A0:6C:65:41:61:F6, Public)` | `NotPaired` |
| Подключение и чтение имени | `MentarisBLE` |
| Три запроса pairing во время соединения | Каждый вернул `NotPaired` |
| Чтение имени после этих запросов | `MentarisBLE`, соединение осталось `Connected` |
| Статус после закрытия соединения | `NotPaired` |
| Второй адрес `CC:78:AB:83:36:02` без предварительного сканирования | `Unknown` |

Первый вариант поиска `DeviceInformation` через `FindAllAsync(AEP)` достиг таймаута
при запросе известного адреса. Заменён на прямое разрешение адреса и чтение
`BluetoothLEDevice.DeviceInformation`. Временная ссылка закрывается; GATT-сессия
для чтения pairing не создаётся. Проверка выше подтверждает сохранение своего
открытого соединения при повторных запросах.

Во время этой проверки реальные `PairAsync`/`UnpairAsync` и Android create/remove bond
не запускались: сопряжение устройств не менялось. Полный аппаратный цикл pair/unpair,
системные PIN-диалоги и Android Bluetooth stack остаются непроверенными.
`Paired` само по себе не устраняет ранее обнаруженный конфликт доступа к `FFB0`.

## Версия 0.2.1-local: типизированный отказ в доступе

Windows JNI передаёт числовой `GattCommunicationStatus` через внутреннее исключение.
Публичный API преобразует `AccessDenied` (3) в `BleError.PermissionDenied`, а
`ProtocolError` (2) — в `BleError.Protocol`; текст ошибки не используется для их распознавания.
Контекст операции, UUID сервиса и нативная причина сохранены в исключении.

`allTests` и `publishToMavenLocal` прошли. Результат: **39 Windows-тестов + 33 Android
host-теста = 72**, ошибок нет. Пять новых тестов проверяют классификацию по коду,
локализованные сообщения, неизвестные статусы, сохранение причины и поведение таймаутов.

Отдельное KMP-приложение с зависимостью `0.2.1-local` из Maven Local скомпилировано
для Android и Windows. При подключении к `A0:6C:65:41:61:F6` воспроизведён реальный
отказ в доступе к характеристикам `FFB0`: приложение перехватило
`BleException.code == PermissionDenied`; нативная причина — `WindowsGattException`.
После перехвата повторное `readDeviceName()` вернуло `MentarisBLE`, приложение завершилось
успешно и закрыло соединение. Это проверка обработки ошибки; доступ к `FFB0` не восстановлен.

## Повторная диагностика «не подключается»

При повторной проверке 30 сентября сканирование за 30 секунд обнаружило 12 устройств,
но ни имени Mentaris, ни адреса `A0:6C:65:41:61:F6` среди них не было. До `connect()`
пример с поиском по имени не дошёл. Причина отсутствия рекламных пакетов не установлена.

Затем `:sample-windows:run --args="A0:6C:65:41:61:F6 --direct --inspect"` завершился
успешно: состояние `Connected`, MTU 23, четыре сервиса, GATT-имя `MentarisBLE`,
модель `NeuroStep`, производитель `Reatech`; сессия закрыта.

Полный пример `MentarisExample.kt` также скомпилирован и запущен в отдельном
KMP-проекте-потребителе через опубликованную зависимость
`dev.gpt.ble:gpt-ble-manager:0.1.0-local` из Maven Local. Результат:
`Connected`, MTU 23, четыре сервиса, `GATT name: MentarisBLE`, `BUILD SUCCESSFUL`.

Все тесты повторно выполнены с `--rerun-tasks`: 19 Windows и 18 Android host, без ошибок.
Сообщение `UncompletedCoroutinesError` при этом не воспроизвелось. По одному стеку без
названия и тела зависшего теста причина его таймаута не установлена.

## Аппаратная проверка Mentaris

У пользователя два устройства. Ранее в отчёте рекламное имя `Mentaris` было ошибочно
объединено с результатами GATT-чтения `MentarisBLE` без разделения по адресам.
После уточнения пользователя повторная проверка установила:

| Адрес | Результат повторной проверки |
| --- | --- |
| `CC:78:AB:83:36:02` | Сканирование: первый пакет без имени, следующий обновил имя на `Mentaris` |
| `A0:6C:65:41:61:F6` | Windows возвращает имя `MentarisBLE` и состояние `Connected` до GATT-запросов диагностической программы; при отдельном активном WinRT-сканировании за 20 секунд от этого адреса получено 0 пакетов (всего 192 пакета от 15 устройств) |

На компьютере также запущен Bluetooth LE Explorer. Наличие процесса само по себе
не доказывает, что именно он удерживает соединение. Независимая диагностическая
программа не включала MaintainConnection и не делала GATT-запросов.

Следующие результаты подключения, чтения и уведомлений относятся к `A0:6C:65:41:61:F6`:

| Параметр | Наблюдение |

| Публичный BLE-адрес | `A0:6C:65:41:61:F6` |
| GATT Device Name `2a00` | `MentarisBLE` |
| Model Number `2a24` | `NeuroStep` |
| Manufacturer Name `2a29` | `Reatech` |

Во время первого аппаратного теста выявлена реакция на начальное событие WinRT

В одном из повторных окон сканирования Mentaris не рекламировался. Подключение по ранее
обнаруженному публичному адресу с использованием Windows cache прошло. Библиотека не
обещает, что уже подключённая периферия продолжит advertising.

## Что не проверялось на аппаратуре

- Android: телефон/планшет не подключён по ADB. Host-тесты не заменяют проверку Android Bluetooth stack.
- Произвольные команды записи в `ffb2`: протокол устройства не предоставлен, команды не отправлялись.
- Запись без ответа, indications и нестандартные MTU на периферии, поддерживающей эти возможности.
- Выключение питания устройства/адаптера, длительная работа и другие Bluetooth-драйверы.

Библиотека реализует центральный BLE-клиент. Режим периферии/GATT-server и автоматический
reconnect не реализованы. Управление pairing добавлено в 0.2.2-local с ограничениями выше.
